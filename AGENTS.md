# Project guidance

- Build a working hackathon MVP around one clear end-to-end demo.
- The idea, challenge track, stack, and deployment target are not selected yet. Do not treat suggestions as decisions.
- Read the current code, README, and `.kiro/steering/` before implementing changes. Once a feature spec exists, read its requirements, design, and tasks in `.kiro/specs/`.
- Use the simplest implementation that satisfies the agreed scope. Verify the main workflow and relevant failure cases with checks appropriate to the chosen stack.
- Keep `.kiro/` and its development artifacts tracked. Record actual Kiro contributions accurately; setup files alone do not establish meaningful Kiro use.
- Keep the public README focused on the product, features, demo, stack, setup, testing, and actual Kiro usage. Keep team assignments and submission checklists on the planning Page.
- Never commit credentials. Document required environment variable names in `.env.example` when integrations are added.
- Inspect Git status before editing. Preserve teammates' changes and use small, focused commits with explicit file staging.
- Update project context when a decision changes. Distinguish proposed work from implemented and verified behavior.
