Trial Prescreening Agent: System Design
Hackachusetts 2026, Healthcare & Biotech track. All patient data in this project is synthetic.

1. Overview
What it is. An AI agent system that finds cancer clinical trial patients for hospital research staff. It reads patient charts against each trial's eligibility rules, removes patients who don't qualify, investigates missing information on its own, and sends likely matches to the coordinator's inbox with the evidence attached.
Who uses it. Research coordinators at small community cancer programs, who currently screen every patient by hand.
The problem it solves. Cancer drug trials are slowed because hospital staff manually read patient charts to find eligible patients, and since most charts are dead ends, eligible patients get missed. Therefore, new treatments reach patients later.
Core principles
    1    AI reads and drafts; code decides. The AI only marks individual rules. Plain code sets every patient's status.
    2    Every decision has evidence. Each result points to a specific line in the patient's chart, and code checks that the evidence is really there.
    3    Nothing leaves the system without a person approving it.
    4    Everything is logged.

2. When it starts and how autonomous it is
One-time setup (a person clicks)
The system does not pull every trial from the government website. A hospital can only enroll patients in trials it has officially opened, so the coordinator tells the system which trials those are.
    1    The coordinator clicks Add trial and enters the trial's ClinicalTrials.gov ID (for example, NCT0XXXXXXX).
    2    The system automatically fetches the trial from the ClinicalTrials.gov API and builds a checklist (section 4.1).
    3    The coordinator reviews and approves the checklist once. This catches any mistake in how the AI read the criteria before it affects hundreds of patients.
From then on, the system runs on its own.

3. Data sources
3.1 Trials
    •    Source: the ClinicalTrials.gov public API (version 2), looked up by trial ID.
    •    What the system uses: the trial title, conditions, phase, recruiting status, the eligibility criteria text, and the last updated date.

4. Step by step
4.1 Trial watcher: turning criteria into a checklist
Triggered by: a trial being added, or a nightly check finding changed criteria.
Input: the trial's eligibility criteria as written, for example:

4.2 Screener: checking the chart against the checklist
Triggered by: an approved checklist, the nightly clinic schedule, new chart lines, or Re-screen now.
Step 1: Pre-filter (code). Only pairs patients with trials for their cancer type, the way a basic records search would. A breast cancer patient is never screened for a lung trial.
Step 2: Read the chart (AI). The AI receives the checklist and the patient's numbered chart lines with dates. For each rule, it returns:

It's instructed to choose unknown whenever information is missing, unclear, or too old, and never to guess. Chart text is treated strictly as data, never as instructions.
Step 3: the results go to the guardrails.
4.3 Guardrails: what the code checks
The guardrails are plain code. They run after every screening and look for these things, in order:
    1    Completeness. Every rule has a result. Any rule the AI skipped becomes unknown.
    2    Valid answers. Results must be met, not_met, or unknown. Anything else becomes unknown.
    3    Citation exists. The cited line must exist in this patient's chart.
    4    Quote matches. The quote must actually appear in the cited line (ignoring punctuation and capitalization). If not, the citation is flagged not verified.
    5    No evidence, no "met." A met with no valid, verified citation is downgraded to unknown.
    6    Time windows, checked by code. For rules with a window, code compares the cited line's date to today. If the evidence is too old, met is downgraded to unknown, even if the AI said otherwise.
    7    Thresholds, where possible. For numeric rules like creatinine ≤ 1.5, code reads the number from the cited line and checks it. If code and AI disagree, the rule becomes unknown.
    8    Safe removals. A not_met only rules a patient out if its citation is verified. An unverified not_met sends the patient to the coordinator as needs review instead, so a patient is never silently removed because of a bad citation.

4.4 Ruled out
    •    The patient is removed from the active worklist for that trial.
    •    They're kept in a Ruled out archive with the failed rule and its cited line, so the decision can be audited.
    •    No coordinator time is spent.
    •    They're re-checked automatically only if the trial's checklist changes, or if new chart information arrives that relates to the failed rule's category (for example, a new pathology report).
4.5 Gap filler: investigating missing information (plans its own steps)
Triggered by: a patient marked needs info.
Goal it receives: "Resolve the unknown rules for this patient, or say exactly what a person needs to get."
Tools it can choose from
Tool
What it does
search_chart(query)
Searches all of the patient's chart lines, including older ones
get_latest(test_type)
Returns the most recent result of a test and its date
check_outside_records(type)
Checks the outside-records inbox
draft_records_request(item, reason)
Drafts a request for a test, scan, or records (needs approval)
ask_coordinator(question)
Adds a question to the coordinator's inbox
finish(summary)
Stops and reports what it found
How it runs: the AI picks one tool, sees the result, and decides the next step, up to 6 steps. Every step is written to the activity log.
What it cannot do: change a patient's status, edit the chart, or send anything. If it finds the missing fact in the chart, it reports the line, and the screener re-runs; the guardrails still decide.

    2    check_outside_records("labs") → nothing new
    3    draft_records_request("liver and kidney panel", "needed within 14 days for trial eligibility")
    4    get_latest("brain MRI") → 5 months ago, outside the 28-day window
    5    draft_records_request("brain MRI", "needed within 28 days for trial eligibility")

4.7 Outreach: messages to the doctor and the patient
Triggered by: the coordinator clicking Verify on a likely match.
1. Note to the patient's doctor
    •    Who the patient is, which trial they may qualify for, and two or three key rules they meet, with evidence
    •    Their next visit date
    •    A clear ask: "Would you like to discuss this trial with them at their visit?"
    •    Delivered through the hospital's internal messaging in a real deployment; simulated in the demo
2. Plain-language summary for the patient
    •    What the study is, what taking part involves, that joining is voluntary and they can leave any time, and that their care team will answer questions
    •    Written at about a 6th-grade reading level, in English, Spanish, Portuguese, or Haitian Creole
    •    Given to the patient by their doctor or the coordinator, not sent directly by the system, because patients should hear about trials from their care team first
Both are drafts until the coordinator approves them.
4.8 After outreach: tracking to enrollment
Outreach isn't the end. The system tracks each patient until they enroll or leave the process.
Stages
    1    Doctor notified: the approved note is sent.
    2    Doctor responded: the doctor agrees to raise the trial, or declines (with a reason).
    3    Discussed at visit: the doctor or coordinator talks with the patient and shares the summary.
    4    Patient interested: or declined.
    5    Consent visit scheduled.
    6    Consented.
    7    Formal screening: official tests confirm eligibility, often within a window of a few weeks before the first treatment. The "verify at visit" items are checked here.
    8    Enrolled, or screen failed (with the reason).
Follow-up agent (automatic)
    •    No doctor reply after 2 business days → reminder to the doctor
    •    The day before the patient's visit → reminder to the coordinator, with the summary ready
    •    Patient interested but no consent visit scheduled after 5 days → reminder to the coordinator
    •    Trial closes or stops recruiting → every active patient for that trial is closed out with that reason
End states: enrolled, declined by doctor, declined by patient, screen failed, or trial closed. Each is logged with a reason, so the program can see where patients drop off.

9. Safety and privacy
    •    Synthetic data only in the demo, clearly labeled on every screen.
    •    The AI never sets a status, edits a chart, or sends a message.
    •    No silent removals: a patient is only ruled out on verified evidence.
    •    Time windows and number thresholds are checked by code, not trusted to the AI.
    •    Patients are never contacted directly by the system.
    •    Everything is logged for review.
    •    It's a prescreening aid. The care team confirms eligibility at formal screening.

10. Testing
Property-based tests (generated random cases)
    •    If any rule is not_met with a verified citation, the status is never likely match.
    •    A citation whose quote isn't in its line is never marked verified.
    •    Evidence older than a rule's time window never produces met.
    •    Every checklist rule always has exactly one result after the guardrails run.
Unit and flow tests
    •    A changed checklist marks old screenings out of date and re-queues patients.
    •    A reply creates a chart line and a re-check.
    •    Drafts can't be sent without an approval action.

12. Impact
    •    Today, staff spend about 7.5 hours of screening per enrolled patient, and two out of three charts reviewed are dead ends.
    •    Similar AI tools have cut chart review time by 50–75%. Applied nationally, that's an estimated 550,000–825,000 staff hours a year.
    •    Catching patients when they first qualify, instead of weeks or months later, gives more patients a chance at new treatments.
